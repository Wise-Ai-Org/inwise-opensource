## Codebase Patterns
- Tests live next to source as `X.test.ts` with a `run()` export and `if (require.main === module) run()`. Build via `npx tsc -p tsconfig.main.json`, then run `node dist/main/X.test.js`. No `npm test` script exists.
- NeDB (`@seald-io/nedb`) without a `filename` option is pure in-memory — perfect for unit tests. Use `new Datastore<any>()` then `await db.loadDatabaseAsync()` before use. `{ field: null }` matches documents where the field is null OR missing (Mongo-compatible), so additive schema changes need no migration.
- Main-process typecheck: `npx tsc -p tsconfig.main.json --noEmit` (silent = success). Renderer: `npx tsc -p tsconfig.renderer.json --noEmit`.
- `import { app } from 'electron'` in plain node is safe at load-time (`app` is `undefined`); it only fails when you actually call an `app.*` method. This means tests can import modules that import electron without booting electron.
- Test-inject pattern for DB-backed modules: export `__setFooDbForTests(db)` that rebinds the module-level `fooDb`. Mirrors `database.ts::__setTasksDbForTests` and the new `sor-write-log.ts::__setSorWritesDbForTests`.
- `preload.ts` `allowed[]` list is for main→renderer **push channels** (`ipcRenderer.on`). New `invoke`-style IPCs do NOT need to be added there. This has been re-confirmed on every story.
- IPC boilerplate for a new channel spans 3 files: `main.ts` (handler), `preload.ts` (invoke wrapper), `renderer/api.ts` (typed method). Keep in lockstep.
- SoR write audit log (`sor-write-log.ts`): every outbound push to an external system wraps the HTTP call with `recordWrite(...)` → network → `markCompleted(...)`. Push functions take an optional trailing `provenance?: WriteProvenance` parameter so callers who know `sourceMeetingId` / `linkedTaskId` / `confidence` / `approvalPath` can attach it. For retry, `pushParams` is stashed on the entry so the write can be re-sent via the raw transport (NOT the wrapper — that'd create a duplicate entry).
- For SoR operations that modify existing records (`update`, `transition`): **GET-before-write** so `fieldDiffs.before` is accurate. PRD accepts the extra round trip.
- Pure helpers `computeCreateDiffs(fields)` and `computeUpdateDiffs(before, updates)` live in `sor-write-log.ts` — free of HTTP, safe to unit-test.

Learnings for future iterations:
- The Jira push wrapper pattern (optional `provenance` parameter + recordWrite/markCompleted around the HTTP body) is the pattern to replicate for every future SoR integration (Salesforce, HubSpot, Linear). Document is in `src/main/AGENTS.md`. Each integration client should expose a `retry{System}Write(id)` that reads pushParams and calls the raw transport directly.
- **Don't wire retry through the wrapper.** The natural instinct is "retry = just call the push function again." That would create a DUPLICATE audit entry because the wrapper always calls recordWrite. Instead, retry bypasses the wrapper and uses the raw transport (`jiraFetch`) to update the EXISTING entry. This keeps retryCount accurate and the audit log honest.
- **Create the local task BEFORE the SoR call.** The PRD asked for `linkedTaskId` in provenance, which is only available if the task exists first. Reordering is a minor behavior change but is strictly better: on SoR failure the local task still exists (previously it was lost).
- **Listener hook vs. NeDB event emitter.** NeDB has no built-in change stream, so a single-registered `onWriteCompleted(listener)` hook inside the module is the cleanest way to push events to IPC. Multiple listeners aren't needed in this architecture — main.ts is the only consumer. If that assumption ever breaks, upgrade to a proper EventEmitter.
- **GET-before-write for accurate diffs costs one extra HTTP per update.** Acceptable per PRD. If a future story needs to batch writes (e.g., importing 100 tasks), consider: (a) skip the pre-GET and record `before: null` for batch imports, or (b) use a single GET-many to hydrate before-values in one call. Not needed today.
- **`computeUpdateDiffs` ignores `undefined` in the updates object**, so callers passing partial update shapes (the common case) don't spuriously record fields they didn't touch. `null` on the other hand is treated as an explicit clear. This matters if you pass `priority: null` intending to clear priority — it will record `{field: 'priority', before: 'High', after: null}`.
- **`targetRecordId: '(pending-create)'` placeholder** is a pragmatic shortcut — we don't know the Jira key until after the API responds. `markCompleted`'s `updates` arg patches the real key on success. A failed create leaves the placeholder, which is queryable and self-documenting.
- **Startup stuck-scan runs after a 15s delay** (not on `whenReady` directly) so calendar sync + daily Jira pull get a chance to run first. No race with those paths, but the delay keeps startup snappy if the user has hundreds of stuck entries.
